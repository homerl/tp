# tp（town portal / 传送门）— 在 SSH 终端里传文件，远端不用装任何东西

> 多跳板机反复传输多份日志实在让人崩溃

在 `ssh` 包一层，在会话里用 `get@!` / `put@!` 传文件，自动校验、断点续传。

### 这个项目最大的特点

简单说一句话：**只要你能在那个终端里敲进字符、也能看到回显，你就能传文件。**
因为 tp 传的只是「你能看到的那些字符」，任何能打字、能看回显的地方，就是它的通道。
打个比方，tp 就像给你已经开着的 SSH 会话开了个「后门小窗」——数据不另开通道，就藏在平时你敲命令、屏幕刷字的那些字符流里，借道现有这条 ssh 连接捎过去。所以它根本不挑环境


## 为什么做这个

你 SSH 到一台机器，想传个文件过来或过去，但：
- 跳板机再次自动跳转,你根本不清楚经过了哪些中间节点
- 多层跳转 + 多个OTP（jump host）时 scp 很麻烦
- 有些环境你只能拿到一个交互式终端，没有别的通道进行传输
- 定制版 / 精简版的 ssh server、堡垒机：运维把该关的都关了
- Terminal 不支持OSC 52

tp 的思路是：**只要有一个 SSH 会话了，那就直接用它传。** 数据走 base64 塞进现有 SSH 通道，远端只需要 `base64` + `dd` + 一个 hash 工具，这些基本每个 Linux 都有。

## 核心特性

- **远端零安装**：不需要在远端装 tp 或任何 agent
- **自动校验**：下载按 4 MiB 分块逐块校验
- **断点续传**：默认开启。中断后重新执行同一条命令，自动从上次断掉的块继续

## 构建

```
go build -o tp .
```

依赖：Go 1.26+，就三个库（`creack/pty`、`xxhash`、`x/sys` + `x/term`）。

## 使用

```
tp ssh <host> [ssh_args]       # 代替 'ssh'，后面参数原样传给 ssh
tp version
```

### 会话内命令

在 `tp ssh` 的终端里直接输入：

```
get@! [-l <rate>|0|1] [-f <log_file>] <remote_path> [local_name]
put@! [-l <rate>|0|1] [-f <log_file>] <local_path> [remote_path]
```

| 参数 | 说明 |
|------|------|
| `-l <rate>` / `-r <rate>` | 限速（**默认不限速**），如 `-l 20K`、`-l 500K`、`-l 2M`，防止堡垒机缓冲区溢出丢字（参数可放在路径前或路径后，本地路径支持 `~/` 展开） |
| `-l 1` | 开启日志/断点续传（**默认就是 1**） |
| `-l 0` | 关闭，纯传不记录 |
| `-f <file>` | 自定义日志文件路径（默认会自动获取断点日志 `<目标文件名>.tprlog`） |

`!get` / `!put` 也照旧能用。主写法把感叹号放到词尾，是因为 bash 只对后面跟着非空格/制表/换行的 `!` 做历史展开：行首的 `!get` 可能被 bash 拦下来报 `bash: !get: event not found`，而词尾的 `!` 是惰性的，一定能送到 tp 手里。命令按整词匹配，所以 `get@!x` 或者只是以 `get` 开头的行会交给 shell。

### 慢链路 / 堡垒机

有些堡垒机会限制粘贴速度，一行一行慢慢吐。tp 读文件比这种链路能带的速度快得多，现在它会如实告诉你，而不是直接报错：自己队列积压时会显示 `link is slower than tp can read: 17 KB still queued`；如果第一轮等待没等到远端回答，它会接着等而不是把一次正常传输判成失败（误报超时会在传输中途重置终端，留下一个你不能信的文件——其实 tp 只是还没看到确认）。

| 变量 | 默认 | 含义 |
|------|------|------|
| `TP_LINK_STALL` | `60` | 写入完全没进展多少秒后判定链路已死 |
| `TP_QUIET_NOTE` | `10` | 静默多少秒后 tp 主动告诉你它还在等（`0` = 不说） |
| `TP_VERIFY_TIMEOUT` | `30` + 每 4 MiB 加 2s | 等远端 checksum 的第一轮时长 |
| `TP_VERIFY_CAP` | `600` | 这个等待的绝对上限 |
| `TP_DEBUG` | 关 | 协议轨迹输出到 stderr |
| `TP_DEBUG_FILE` | 关 | 轨迹输出到文件（不弄花进度条） |

### 网速明明很快，但逐行慢得要死：这条链路是按行收费的

先认一下这个症状，别误会 tp：在堡垒机会话里用 screen 往上翻屏，100 行可能 5 分钟都滚不完，粘贴也能肉眼看见一行一行刷；但 scp 一个大日志到另一台机器上飞起。带宽在，不在的是“到屏幕”这条路。

这个坑网上一大堆同名兄弟，中间人们做的取舍都一样：按**行 / 屏**收费，不按字节，因为它得保证你还敲得动键盘。tmux 作者解释为什么 tmux 比 ssh 慢时说得最清楚：“ssh 很乐意把 TCP 缓冲灌满让终端自己慢慢啃，它唯一关心的响应就是 ^C”，所以 tmux 一积压到八屏左右（`TTY_BLOCK_START` = 列数 × 行数 × 8）就主动减速、改成重绘——窗口越大，税越重。EternalTerminal 的流控直接就是 1024 行/秒，所以 `cat` 一个没有换行的大文件反而飞快。浏览器终端（xterm.js 那一类）又叠了一层自己的帧率，还把 native 终端从内核免费拿到的背压弄断了。堡垒机厂商自己也踩：JumpServer 有个 bug 就是 web 终端用 sz 下载超过 ~100 KB 卡在 99%。

对 tp 意味着什么：

- **上传基本没事。** 这个方向是输入，tp 本来就假设有些堡垒机逐字符慢慢吐（见上面的 `link is slower than tp can read`）。而且上传命令会在远端先 `stty -echo`，在这类链路上尤其重要：开着回显的话内核会把整个 base64 本体原路回显回来，每个字节都要被渲染两遍。
- **下载才是风险所在。** 一个 4 MiB 的块离开远端时是 5.6 MB base64、175 个长行（`base64 -w 32000`），100 MB 总共才 ~4400 个换行——如果计费单位是流里的换行，很便宜。但如果那个 shell 挂在一个**已 attach** 的 screen/tmux 窗口里，多路复用器得把这堆流画进自己的窗口，而它是按窗口宽度折行的：5.6 MB 除以 80 列 ≈ 每块 7 万行，100 MB ≈ 170 万行。这就是一分钟和一下午的区别。

优化之前先测。在堡垒机会话里跑一遍，screen 里一遍、screen 外一遍，差值就是多路复用器收的税：

```bash
dd if=/dev/zero of=/tmp/50m.bin bs=1M count=50

# 1 纯网速，完全不碰屏幕
time dd if=/dev/zero bs=1M count=50 2>/dev/null | base64 | wc -c

# 2 同样的字节，但必须画到屏幕上
time base64 -w 0 /tmp/50m.bin > /dev/tty

# 3 一行多少钱：2000 行 vs 同样字节数 0 换行
time seq 1 2000 > /dev/tty
time seq 1 2000 | tr '\n' ' ' > /dev/tty

# 4 一次往返多少钱
time (for i in $(seq 30); do echo x > /dev/tty; done)
```

怎么读：1 快 2 慢 → 钱是按“画”收的，tp 的下载一定会付。3 的第一条远慢于第二条 → 计费单位就是换行。1、2、3 都快，只有 screen 滚动难受 → 那就是终端难看，tp 没事。第 4 条那个数 × 行数 = 你的时间下限。

能做的事，按杠杆从大到小：

1. 大文件传输别在 attach 着的 screen/tmux 窗口里做——否则每个 base64 字节都要在被送到你手上之前被解析、被画、被重发一遍。
2. 把窗口拉宽（字号调小，300~400 列）。多路复用器按窗口宽度折行，列数 ×4 就是要画的行 ÷ 4。tp 会把你真实的窗口尺寸告诉远端，所以这个能一路穿透。
3. 大输出别进 tty：`cmd > /tmp/x 2>&1` 再 `less /tmp/x`。没进 pty 的字节不收费。
4. screen 里可以 `defbce on`，重绘时少发字节。别去碰 `defflow`：XON/XOFF 穿过一整个代理链，锁死的概率比提速的概率大。

### 下载不会闷着不出声

下载这条路上没有任何超时——get 等到 `__TP_DONE__` 才算完，而进度条只有字节到了才动。所以在会滴水的链路上，屏幕就是停在那里不动，而其实一切正常——看起来跟程序挂掉一模一样（也确实被当成挂掉报过）。所以现在 get 进行中时，有个看门狗会开口说话：静默 10 秒开始，然后 25 秒、1 分钟、2 分钟、5 分钟：

```
[tp] … still waiting for the remote to answer: 12s of silence, nothing received yet
[tp] … still waiting for ./big.bin: 25s of silence, 4.20 MB/100.00 MB received
[tp] … still waiting for ./big.bin: 25s of silence, 4.20 MB/100.00 MB received, tp is still pushing 1.2 KB
```

最后那行最有用：tp 自己还积压着字节，说明链路在限**输入**；队列空着而依旧静默，那就是远端（或者替远端渲染的那个东西）扣住了数据。字节一动，阶梯重置，所以只是慢的传输不会吵；真的卡住的会拿到最后一句，那句话把两种“坐在这把椅子上看起来一模一样”的解释都念出来，然后闭嘴。`TP_QUIET_NOTE=30` 把整个阶梯后移，`0` 关掉。

### 典型工作流

```bash
$ tp ssh jump1 -p 2222          # 代替 ssh jump1 -p 2222
# ... 手动跳转到目标机器 ...

# 下载
get@! /tmp/bigfile.bin
[tp] ↓ 1.2 GB → ./bigfile.bin (resumable)
[tp] ✓ ./bigfile.bin (1.2 GB) 42.3s 29.15 MB/s avg

# 上传
put@! ./local.txt /tmp/remote.txt
[tp] ↑ ./local.txt (3.4 MB) → /tmp/remote.txt
[tp] ✓ /tmp/remote.txt uploaded OK

```

中断（Ctrl+C 或网络断了）后重新执行同一条 `get@!` / `put@!`，会从断点继续：

```
[tp] ↻ /tmp/bigfile.bin → ./bigfile.bin (resume from block 87)
```

### 退出

- 双击 Ctrl+C（1.5 秒内按两次）退出 tp，终端自动恢复
- 单次 Ctrl+C 转发给远端（中断远端前台进程）
- 远端 `exit` 也会退出

## 调试

tp 靠两个环境变量输出自己的协议轨迹——故意没做 `--debug` 参数，因为 `tp ssh` 后面的东西是原样透传给 ssh 的，放个 flag 在那儿分不清是给你的还是给 ssh 的。

```
TP_DEBUG=1 tp ssh host                     # 输出到 stderr
TP_DEBUG=1 TP_DEBUG_FILE=/tmp/tp.log tp ssh host   # 输出到文件
```

传文件的时候建议用 `TP_DEBUG_FILE`：进度条是用 `\r` 在同一行反复刷的，debug 打到同一个终端会把它花掉。

日志带时间戳，两个方向都记：tp 注入了什么、远端答了什么、哪些行被认成协议标记、哪些被当成 shell 回显的命令丢掉了：

```
11:46:52.656 drop echo of injected command (nonce 286ff10b9b170f89)
11:46:52.659 __TP_TMP_SIZE__ response: size=4194304
11:46:52.659 probe answered: 4194304
11:46:53.379 __TP_DONE__ response: remote sha "be27c93d..."
```

大段数据只留前 120 字节，并告诉你隐掉了多少，所以传 20 MB 不会把有用的几行埋掉。

## 工作原理

### 整体架构

```
你的键盘
    │
    ▼
┌──────────────────────────────────────────────┐
│  tp (本地进程)                                │
│                                              │
│  stdin reader ──→ 直接转发按键               │
│       │                                      │
│       ├── 识别 get@! / put@! 命令              │
│       │                                      │
│       ▼                                      │
│  PTY (tp ↔ ssh)                              │
│       │                                      │
│  output reader ──→ 解析 __TP_*__ 标记        │
│       │         吞掉已释放命令行的回显        │
│       │         base64 流式解码 → 写文件      │
│       ▼                                      │
│  stdout → 你的屏幕                           │
└──────────────────────────────────────────────┘
    │
    ▼ SSH 隧道
┌──────────────────────────────────────────────┐
│  远端 shell（无 tp）                          │
│  执行注入的 shell 命令：                      │
│    下载: dd + base64 分块输出                 │
│    上传: head -n N | base64 -d → 写临时文件   │
└──────────────────────────────────────────────┘
```

### 下载 (get@!) 流程

1. tp 往 SSH 通道注入一条 shell 命令，远端用 `dd` 按 4 MiB 分块读文件
2. 每块先发一个 `__TP_BLOCK__ <序号> <校验和>` 标记，再发该块的 base64
3. 本地 output reader 解析标记、流式解码 base64（O(1) 内存）、逐块校验
4. 校验和通过 → 追加到临时文件 + 写入 `.tprlog`
5. 全部完成后 `__TP_DONE__` 触发：rename 临时文件到目标，删除日志
6. 任何一步失败：删除临时文件，保留日志（供续传），原文件不受影响

### 上传 (put@!) 流程

1. tp 先探测远端目标是否存在（`__TP_EXISTS__`），存在则弹 y/N
2. 注入 `head -n N | base64 -d > tmp` 命令
3. 本地按 4000 字符/行把 base64 数据喂进 PTY（避开 4096 行缓冲限制；开启 `-l <rate>` 限速时自动缩短行宽并匀速发送）
4. `head` 读满 N 行自动退出（不依赖 ^D，多层跳转安全）
5. 远端校验临时文件大小 → rename 到目标 → 回报 sha256（`__TP_DONE__ <sha>`）
6. 本地比对 sha256，通过才算成功

### 谁负责回显

一块屏幕只能有一个人画：**远端 shell 回显，tp 只负责转发**——跟原版 `ssh` 一样的分工，也是唯一能保住行编辑的分工。
tp 把自己的终端设成 raw mode（这样每个按键都能立刻拿到），把跟 ssh 之间的那个 pty 也设成 raw mode——但 `ECHO` 这一位故意不动。因为 ssh 会把它自己 stdin 的 termios 拄进 SSH 的 `pty-req` 里，这一位决定的是**远端** pty 开不开回显；而 bash 的 readline 每次提示符只会判断一次要不要自己画：在“不回显的终端”上它认定自己接的是一台不发声的机器，于是 ↑ 召回历史、Tab 补全、Ctrl+R 全都会静悄悄发生——命令照旧执行，屏幕上什么都没有，看起来就像终端不刷新。

tp 以前在这里清掉了 `ECHO`，然后自己逐键回显。于是远端没东西可画，两个画家永远碰不上面——直到有人按了 ↑：readline 有东西要画，而 tp 根本无从知道。本地回显还会重复擦除（tp 的 `\b \b` 加上 readline 的 `\b\e[K`，多擦一格，把提示符都擦掉一角），而且会把你的密码明文画在屏幕上。

现在本地回显只留在两个地方，因为那些字节确实不会到远端：你正在敲的 `get@!` / `put@!` 那一行，以及覆盖确认的 y/N。还有一种例外：你以为是在敲 `get@!`、结果是 `git status`——tp 已经把这些字符画上屏了，交给远端时会把他们放进 `echoSuppressor`，把远端的那一份吞掉。

### 为什么 tp 的命令不会进你的 shell 历史

tp 传文件是靠往你的会话里注入一条很长的 shell 命令。每条注入的命令前面都带一个空格，所以只要远端 bash 设了 `HISTCONTROL=ignorespace` 或 `ignoreboth`（Debian、Ubuntu 默认就设），这条就不会进 history——按 ↑ 召回的还是你自己的命令，而不是那条 1200 字符、一按回车就重传一遍的一行命令。远端没设这个的话，空格被忽略，tp 的命令会进 history，不影响正确性，只是翻历史时吵一点。

### 断点续传机制

- 日志文件 `.tprlog`：首行是 `<文件名> <总块数>`，之后每行 `<块号> <校验和>`
- 下载续传：检查日志 + 本地临时文件的最后一个块校验和，通过则从下一块继续
- 上传续传：探测远端临时文件大小 + 最后几块的 xxh64，和本地日志比对，找到最新完好块
- 日志文件在传输成功时自动删除

## 协议标记

| 标记 | 方向 | 用途 |
|------|------|------|
| `__TP_BEGIN__\|name\|size\|blocks` | 远端→本地 | 下载开始 |
| `__TP_BLOCK__ <n> <cksum>` | 远端→本地 | 新块开始 |
| `__TP_DONE__ [sha]` | 远端→本地 | 传输结束（上传时带 sha256） |
| `__TP_ERROR__ <msg>` | 远端→本地 | 错误 |
| `__TP_EXISTS__ yes\|no` | 远端→本地 | 目标文件存在探测 |
| `__TP_TMP_SIZE__ <n>` | 远端→本地 | 上传续传：远端临时文件大小 |
| `__TP_CKSUM__ <c1> <c2>...` | 远端→本地 | 上传续传：远端临时文件块校验和 |

注入的命令里标记被拆成 `__TP_""DONE__` 的形式（空字符串拼接），这样 shell 回显命令本身时不会误触发本地解析。每条注入命令还带一个随机 nonce（shell 注释），用来识别并丢弃远端对命令的回显。

## 兼容性

**远端要求**（基本都有）：
- `base64`（GNU 或 BSD）
- `dd`
- `xxh64sum`（优先）或 `sha256sum` / `shasum` / `sha256`（至少一个）
- `stat`（GNU 或 BSD）、`wc`、`head`、`mv`、`rm`

**本地要求**：
- 仅 Linux（用了 unix ioctl）
- Go 1.26+ 构建

**已知限制**：
- 需要交互式 SSH 会话（非 `ssh host command` 模式）
- 路径中不能包含引号、`$`、反引号、反斜杠、`!`（防注入）
- 单条注入命令不能超过 4095 字节（PTY canonical mode 行缓冲限制），极长路径可能触发截断
- ↑ 召回历史、Tab 补全、Ctrl+R 现在都能用，因为回显的是远端。如果遇到某个堡垒机强制把 pty 设成不回显，那打字就是看不见的——跟直接用 `ssh` 一模一样
- 上传时 tp 会先在远端 `stty -echo`：否则内核会把上传的每一个字节原样回显回来，3 MB 的文件变成 4 MB base64 往回砸，还是砸在这条链路上最慢的那一段
- 定位就是开一个 bash 终端频繁上传下载小块文件，所以没往更复杂的方向改进（没有终端模拟器，也没有屏幕模型）
- 目前只测了 bash，没大范围测过其他 shell / 终端
